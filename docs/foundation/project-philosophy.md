# Назначение и приоритеты

YTDownload загружает видео, аудио и плейлисты через yt-dlp и FFmpeg, сохраняет историю и сопутствующие материалы. Пользователи — человек и программные клиенты. Нужен один понятный прикладной API, к которому можно подключать CLI, MCP и графическую оболочку без повторения правил.

Приоритеты: сохранность данных и приватность → правильный результат и честное описание отказа → совместимость действующих входов → понятная архитектура → удобство дальнейшего расширения. Работающее приложение важнее количества классов, документов и агентов.

Исходная архитектурная задача — рефакторинг уже существующего Python-приложения с `ApplicationAPI`, CLI, MCP и PySide6. Их наличие само по себе не доказывает независимое ядро или общий живой процесс. Актуальное устройство устанавливают по исходникам и выполненным проверкам; план и доказательства исполнения разделены. Начальный план Oracle сохраняет своё историческое назначение, но не делает Oracle обязательным планировщиком последующих задач.

## Command-first, а не CLI-first бизнес-логика

- Прикладная команда выражает намерение выполнить действие; запрос читает состояние. Они не обязаны быть строками shell или отдельными классами.
- Предметные правила принадлежат `src/domain/`; прикладные сценарии и согласование эффектов — `src/application/`; реализация ввода-вывода — инфраструктуре. CLI-парсер, FastMCP и Qt не определяют правила ядра.
- Адаптер преобразует ввод, вызывает общий API и оформляет ответ. CLI не вызывает MCP для повторного использования правил, MCP не запускает CLI, GUI не обязан управлять CLI-подпроцессами.
- Каждое изменяемое состояние имеет одного авторитетного владельца. Общая библиотека и один JSON-файл на диске сами по себе не создают общую живую очередь между процессами.
- Прямой Python-вызов и работа без `QApplication` — обязательные проверяемые свойства ядра. Создание API не должно само открывать окно или запускать сервер.
- Профиль A/B/C/D, владение задачами, долговечность и способ размещения выбираются по нужным гарантиям. Очередь, IPC, Command Bus, CQRS, журнал событий и workflow не вводятся ради названия паттерна.
- Принятие задачи, её выполнение, запись истории, получение ответа и доставка файлов — разные события. Прекращение ожидания и запрос отмены не означают фактическую остановку исполнителя.
- Для каждого режима надо явно сказать, что остаётся после завершения вызова/процесса. Команда управления чужой живой очередью не должна молча создавать независимую очередь.

## Сохранность и совместимость

Сохраняем работающие загрузки, форматы истории/настроек и существующие входы, если конкретная несовместимость не описана и не обоснована в плане. Не меняем внешний вид, вкладки, темы, надписи и взаимодействия GUI. Минимальная совместимая проводка GUI к новому ядру допустима только как необходимая часть отделения ответственности, с регрессионной проверкой; развитие интерфейса — другая задача.

Удаление и отмена имеют явные предусловия и эффекты. Предпросмотр не меняет данные; перед эффектом повторно проверяются изменяемые условия. Не удаляем общую папку или чужие результаты только потому, что путь встретился в истории. При ошибке не выдаём частичный исход за полный успех; неизвестное остаётся неизвестным. Повтор после потерянного ответа требует сверки состояния, а не слепого повторения эффекта.

Реальные пользовательские настройки, история, загрузки, журналы и credentials не являются тестовыми данными. Не выполняем сетевые загрузки без отдельного разрешения с конкретным URL. Не меняем глобальные настройки Pi/Hermes и соседние проекты. Коммиты, push, выпуск, установка пакетов и загрузка исполняемых файлов не разрешаются одним архитектурным планом. Для этого проекта отдельно разрешена только selective Git-доставка уже принятого среза тем же Reviewer по [порядку команды](../agent-team.md); остальные границы сохраняются.

## Проверка поведения

Тест должен обнаруживать неправильный результат, а не подтверждать наличие нового класса или количество вызовов. На настоящем пути проверяем вход → реальный прикладной владелец → эффект/сохранение → повторное чтение. Подменяем yt-dlp/сеть на границе инфраструктуры, но не проверяемое ядро или репозиторий. Для сохранения нужны различимые данные и readback; для отказа — отсутствие недопустимых эффектов; для асинхронности — применимые отмена, позднее завершение, освобождение ресурсов и следующая операция.

Начинаем с узкой регрессии и сохраняем исходный отказ. Общая смена API и bootstrap обосновывает полный offline-suite и проверку действующих адаптеров. Unit, offline integration, реальная MCP stdio-сессия, offscreen GUI smoke и YouTube E2E — разные доказательства. Процент покрытия, линтер и структурный checker не доказывают работоспособность приложения. Невыполненное — `NOT_RUN`, skipped — не PASS.

Рабочий порядок и команды принадлежат [инструкции тестирования](../../.github/instructions/testing.instructions.md), конечные обязательные проверки — [quality gates](../agent-instructions/05-quality-gates.md). Нельзя ослаблять проверку ради зелёного результата или выдавать старый baseline за новый дефект без сравнения.

## Полезная и безопасная диагностика

Состояние определяет прикладной владелец, а не лог. Нужны значимые начало, принятие, результат, отказ и cleanup; существующий ID задачи связывает их без нового tracing framework. Разрешены проверенные технические коды, стадии, причины, количества и длительности с единицами. Неизвестное число не превращается в ноль.

Секреты, прокси с credentials, URL, названия/пути пользовательских файлов, описания и субтитры по умолчанию не логируются. DEBUG увеличивает подробность, но не права. Текст исключения и traceback тоже могут раскрывать данные; их нельзя считать безопасными автоматически. CLI stdout с запрошенным результатом и MCP protocol output — не диагностический журнал: данные там выдаются по явному пользовательскому запросу, а не дублируются в лог.

Используем существующий `src/core/logging_setup.py` и стандартный `logging`. Проверяем непустой настоящий выход emitter → filter/formatter → handler → flush: полезные факты присутствуют, запрещённые синтетические маркеры отсутствуют. Фактическая ротация: `app.log` 10 MiB × 5 backup и `app.error.log` 5 MiB × 3 backup; автоматический срок удаления по возрасту не установлен. Отдельный безопасный DEV/export/telemetry-контур не считается реализованным без кода и проверки. Внешняя отправка диагностик и аналитики требует отдельного согласия.

Порядок изменений, владельцы и ограничения — [инструкция логирования](../../.github/instructions/logging.instructions.md). Этот документ не сертификат приватности существующего кода.

## Знания и конечность работы

У правила один владелец. Исторический план сохраняет причины, но не выдаётся за текущую архитектуру. Автор обновляет затронутый контракт, команды и руководство в том же логическом результате; отсутствие влияния объясняет. Философия задаёт причины, инструкция — действия, план — предстоящие срезы, отчёт — фактически выполненные проверки. Принятие этой философии означает принятие инженерных принципов, не реализацию всего command-first-контракта; состояние срезов — в [проверке](../command-first/VERIFICATION.md).

Coder получает средние–крупные связные задачи и проверяет результат; независимый Reviewer принимает завершённый замороженный кандидат. Oracle подключается только при конкретных затруднениях, существенной неясности или безрезультатном ремонте; достаточный план не пишется заново перед каждым срезом. Обязательные замечания возвращаются тому же кодеру, затем тому же проверяющему. После технического ACCEPTED Reviewer завершает документы/инструкции и разрешённый commit/push, а Coder может сразу работать над следующим непересекающимся срезом: принятые байты сохраняются, владелец index один. Порядок и точные назначения — в [команде Pi](../agent-team.md). Hermes — тонкий оркестратор, а не второй автор или второй проверяющий. Работа закончена при выполнении исходных критериев, а не после написания плана; соседние улучшения не расширяют её бесконечно.
