# Роли

| Роль | Задача | Provider / model | Запрошенный уровень Pi |
|---|---|---|---|
| Oracle | Разбирать конкретное затруднение, существенную неясность или безрезультатный ремонт; не обязательный планировщик каждого среза | `openai-codex` / `gpt-6-astra` | `xhigh` (Extra High) |
| Coder | Реализовать средний–крупный связный срез и тесты, реально проверить результат, передать замороженный кандидат | `openai-codex` / `gpt-6.1-sol` | `max` |
| Reviewer | Независимо принять точный кандидат; после ACCEPTED завершить документацию/инструкции, selective commit и push/readback | `openai-codex` / `gpt-6.1-sol` | `max` |

Это явное назначение пользователя для этого проекта, не наследование модели Hermes. Фактические model/thinking события проверяются в новых записях native Pi-сессии; одна launch-команда подтверждает намерение, а не исполнение. Если установленный provider преобразует уровень, отдельно записывается фактическое отображение без выдуманного «Max».

Начальная адаптация инструкций и философии предшествует передаче реализации в Pi. После передачи Hermes только ставит задачи, хранит ссылки на сессии/артефакты, управляет владельцами и возвращает замечания. Не читает заново весь код и не исправляет его вместо назначенных агентов. Этот документ принят как проектный порядок работы, не как приёмка всего рефакторинга.

## Рабочий цикл

1. Hermes передаёт Coder один средний–крупный связный срез: цель, критерии результата, применимые документы, владельцы и границы. Не дробить работу на микрозадачи, но и не объединять несвязанные изменения в одну дорожную карту. Достаточный существующий план/контракт переиспользуется; отдельный вызов Oracle перед каждой задачей не нужен.
2. При конкретной проблеме, которую не удаётся решить, существенной неясности или повторном безрезультатном ремонте подключается тот же Oracle с оригинальными требованиями, наблюдаемыми отказами и точным вопросом. Он исследует и предлагает решение/необходимое уточнение плана, не меняет продуктовые исходники и не заменяет независимую приёмку. Закрытие начальной миграции не переоткрывается ради повторного планирования.
3. Coder реализует и проверяет весь связный срез, фиксирует фактические результаты, замораживает полный кандидат и освобождает пересекающиеся файлы/ресурсы до review. Не stage/commit/push. Reviewer работает в отдельной истории, не принимает авторский PASS за свой; до технического verdict исходники, tests/scripts и index read-only.
4. Reviewer возвращает завершённый технический ACCEPTED/NEEDS_CHANGES/ORACLE_REQUIRED для точного состава/байтов с exits, NOT_RUN и ограничениями. Обязательный новый провал не становится ACCEPTED из-за авторского PASS. Замечания через Hermes возвращаются тому же Coder; исправленный кандидат — тому же Reviewer, с переиспользованием применимой неизменной проверки.
5. После технического ACCEPTED и освобождения пересекающихся ресурсов Hermes сразу может передать Coder следующий разрешённый непересекающийся срез. Завершённый ответ о приёмке — отдельная граница, а не обещание, что кандидат, вероятно, хороший. До ACCEPTED следующий зависимый срез не запускается.
6. Одновременно **тот же Reviewer**, продолжая ту же сохранённую беседу, завершает затронутые документы/инструкции и проверки их final bytes, затем является единственным владельцем index/commit/push. Не откладывать это до конца проекта и не ждать его окончания перед независимой работой Coder. Разрешение действует для принятых срезов в `refactor/command-first`, без нового человеческого согласования каждого commit. Явные пути/при необходимости hunks, проверка index/path set/content/parent; без `git add -A`, stash/reset/rewrite и посторонних изменений.
7. Push только принятых commits в существующий project remote: зафиксировать принятый SHA и использовать явный `<accepted-sha>:refs/heads/refactor/command-first`, не полагаться на движущийся HEAD. Без tags/force/main/release и изменения remote/visibility. До записи проверить destination/outgoing history и применимые CI/branch policies, после — exact remote SHA. Неопределённый ответ требует readback, не слепого retry. Техническое acceptance, документация, local commit, push/readback и remote CI различать; auth wall — delivery blocker, не разрешение извлекать credentials и не запрет следующего независимо разрешённого coding-среза.

### Параллельное завершение без пересечения владельцев

Перед запуском следующего среза явно разделить пути/участки записи и стабильные общие входы. Reviewer завершает только принятую предыдущую работу и её документы; Coder не меняет эти документы и принятые исходники до их commit, не трогает index. Если следующий срез действительно пересекается с ещё завершаемым, сериализуется только конфликтующая часть, а не вся очередь.

Принятый кандидат остаётся замороженным. Состав commit проверяется по его манифесту и отдельно проверенному документационному delta; непринятые изменения следующего среза не добавляются. Учтённые незакоммиченные изменения вне доставляемого состава не требуют глобальной чистоты дерева, stash/reset или остановки независимого кодера. После доставки сохраняется точная идентичность опубликованного среза, а не текущего дерева следующей работы.

Не запускаем двух писателей одних файлов. Разные роли имеют постоянные UUID и пути native session JSONL; для продолжения используется `--session <проверенный существующий файл>`, а не новая беседа с тем же именем. Сессии и полные журналы Pi остаются в обычном домашнем хранилище Pi, не включаются в Git.

## Использование установленного Pi

На начало работы проверен Pi `1.3.0`. Используются существующие вход и авторизация `openai-codex`; credentials не извлекаются и не копируются. Глобальные настройки, extensions и профили не меняются. Не устанавливаем дополнительную агентную платформу.

Из корня проекта для Oracle:

```bash
pi --provider openai-codex --model gpt-6-astra --thinking xhigh --no-skills --skill tools/project-foundation/skills/pf-plan/SKILL.md --skill tools/project-foundation/skills/pf-command-first/SKILL.md
```

Для Coder/Reviewer — та же установленная программа, но отдельные беседы и `--model gpt-6.1-sol --thinking max`. Это пример настройки маршрута, не автоматическая выдача роли или прав. Полное задание передаётся через `@<brief.md>`; для контролируемого запуска `--no-context-files` допустим только с явным чтением корневого AGENTS и сохранением домашних защитных ограничений.

Исполнители используют доступные Serena, codebase-memory и ast-grep по необходимости, не запускают все анализаторы ради галочки; перед выводом об отсутствии символа проверяют корень и актуальность индекса. Эти же границы передают внутренним читателям. Внешний поиск не заменяет текущие исходники; разрешение на работу не разрешает чтение исключённых данных или отправку секретов.

## Неприкосновенные границы

Без изменения GUI-дизайна, удаления пользовательских файлов, запуска реальных YouTube-загрузок, установки/обновления зависимостей или выпуска. Единственное Git-исключение — описанная выше selective доставка уже принятого среза тем же Reviewer; иных прав этот порядок не даёт. Проверки используют временные синтетические данные; для реальной загрузки нужен отдельный конкретный URL и разрешение. Нельзя отключать guards/approvals ради запуска.
